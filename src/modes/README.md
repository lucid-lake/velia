# Modes

Public names (owner, 2026-10-29): Cruise · Sail · Regatta · School (`src/modeNames.js`). Folder names stay as they were.

**The mode registry** (`src/modes/registry.js`; its pure names in `src/modes/rows.js`, read by what only names the modes, Velia v2 too): one row per mode (`id`, `label`, `aliases`, `card`, `order`, `dev`, `load`). `src/main.js`, `src/modeNames.js`, the home card's picks, the card classes, the watchdog and `tools/loading_shell.py` read it. A new mode is one row plus its folder; `checkRows` throws on a malformed row (`tests/modeRegistry.test.mjs`).

**The features list** (`src/features/index.js`): what a mode or the core adds to the lake, one row each (`id`, `scope` core | mode, `modes`, `on`, `load`, `attach`, `settings`, `shown`, `timeRows`): the fireworks (core), the racing marks (Sail, Regatta), the kayak demo stage (Sail, `?kayak=`) and the kayak fleet (Sail, Cruise). They attach in one loop, `attachFeatures(core, player, { scope, mode, ctx })` → `{ ids, get(id), update(…), dispose() }`; the clock menu's Fireworks row and the Setup rows (camera to kayaks, the radio) come from the rows. A new mode that wants the fleet adds its id to the row's `modes` (`tests/features.test.mjs`).

A mode is what the player does on the lake. The core (`src/core/`) is the lake itself: the renderer, the sky, the world, the wind, the sound beds, the loading-screen hooks, the capture contract and the loop. It loads once for every mode. `src/main.js` picks the mode from the URL and loads only that one, with a dynamic `import()`, so each mode is its own chunk.

## The shared helm layer (`src/sail/`)

What more than one mode sails with lives in `src/sail/`, not in a mode's folder (refactor Phase 2 step 5): the boat's assembly (`assemble.js`), the live controls and their parts (`controls.js`, `sheets.js`, `pads.js`, `feel.js`, `rumble.js`, `course.js`, `tackCarry.js`, `seamanship.js`, `grounding.js`, `keys.js`, `skills.js`), the captain's tools, the logbook and the chart (`captainTools.js`, `logbook.js`, `chart.js` and theirs), Sail's options and start (`options.js`: Regatta starts from them, Cruise's hand-over puts them in force), and the physics' fixed step:

- `stepper.js`: `createStepper({ dt: 1/60, maxSteps })`, the one 1/60 s accumulator (`advance(simDt, tick)`, `alpha` for the drawn pose: src/boat/interp.js) and `clampFrame(dtRaw)` (the 100 ms frame cap).
- `simulation.js`: the pure `Simulation`, `step(dt, inputs) → state` over the boats' physics, with no DOM, camera or `window`. Inputs are plain data (the helm, the sheets, the sails' furl, the reef, pro trim, `engine` on/off and the `throttle`, `anchor` down/up with a tackle); the world comes in through each boat's `env(t)`; `snapshot()` / `restoreSimulation()` / `encodeState()` give the whole state as plain data that steps on bit for bit (the base for multiplayer). Sail's controls, Cruise (`chill/helm.js`), the Regatta session (a two-boat fleet), and the headless voyages, races and surf runs all step their boats through it. tests/sim-*.test.mjs check each mode's 120 s run, live and pure, against main's record, tick for tick.

- `src/craft/` (refactor round 2, Phase C step 5): what the player steers. `CRAFTS` (`sloop`, `kayak`), `craftOf(vessel)` (the profile's `craft` field; none is a sloop), `vesselFor(id)`. Each craft row has `id`, `kind` (the player's: `sail` | `paddle`), `inputs`, `createPhysics(start)` and `restorePhysics(data, params, vessel)`; the Simulation builds and restores each boat's physics through it, and a snapshot names its craft by `vesselId`. The sloop is `BoatPhysics`; the kayak is `KayakPhysics`, the lake fleet's hull model (`src/kayaks/agent.js stepHull`) on its own profile `src/craft/kayak/vessel.json` (not a home-card row). tests/sim-snapshots.test.mjs (+ slow lane) gates the snapshot bytes on every voyage seed.
- The boat's assembly in parts (Phase C step 6): `src/sail/assemble.js` is a composer over `src/craft/hull.js` (the floating frame any craft shares: the craft's physics, float/wake/spray, follow camera, air, bottom, posts and `env`; no loaders, so it runs in node; `boatAudio` stays in it until the audio seam), the sloop's `src/craft/sloop/body.js` (its GLBs and materials), `rig.js` (spars, fittings, sails, in three phases around the body so the attach order holds; a paddle craft throws) and `capture.js` (the headless settle, the capture camera and the film contract). The call order is the contract; the `boat` service keeps its twelve keys (tests/pages/boatService.page.mjs).
- Camera settings from the craft (Phase C step 7): `craft.cameras(vessel)` → `{ follow: { hull }, helm: { eye } }` (`src/craft/sloop/cameras.js`, read from the profile's `cameras` block; `camerasFor(vessel)` in `src/craft/index.js`, empty rows for a craft with none). The follow camera's length unit (`FollowCamera({ hull })`, `createHull`), the helm view's eye (`HelmCamera(helm)` in the controls, Cruise's rig and the capture path) and the binoculars' eye come from it; `FOLLOW.hull` and `HELM_CAM.eye` are only the defaults. Halcyon's numbers are unchanged (9.1 m; [0, 2.0, 3.3] m). tests/craftCameras.test.mjs.
- The controls split (Phase C step 8): `src/deck/index.js` `attachDeck(core, player, { helmCam, view, cruiseKey })` is what any craft's live page shares: the held keys, the mouse (press, drag, wheel, click), the tool dock (`mountDock`: chart, logbook, helm, cruise, keys), the views and their camera chain (`setView`, `camera(dt, { rs, pose, look, viewLook, zoomMul, lean, scene, outer })`), the top bar (`mountBar(hooks)`: `subtitle`, `windPick`, `quiet`, `log`, `clockMenu`) and its keys (C, Shift+C, the Cruise key; a controller adds its own with `onKey(fn)`). It imports no sail code; the controller answers through `setHooks({ onPart, onClick, clickBlocked, aiming })`. `src/controllers/sail.js` `attachSailController(core, sail, deck, { handover, helmPick })` is the sloop's: helm, sheets, pro, skills, hints, seamanship, the helm station and the physics tick. `src/sail/controls.js` is a shim (`attachControls` builds both) until Phase D. The DOM order, the listeners and one frame's call order are fixtures recorded before the cut (tests/sailDomOrder, tests/sailFrameOrder; tools/sail-order.mjs).
- The audio and lesson seams (Phase C step 10): a craft row may give `createAudio(core)` → its own sound (`{ update(t, state, o) }`, plus `dispose()` if it has one); the hull frame calls it on a live page (none in captures; a craft without one is silent). The sloop's is the boat's sound (`src/craft/sloop/audio.js` over `src/boatAudio.js`, the same banks and seed). A craft row names its lesson set (`lessons: 'sail'`); `src/lessons/index.js` `lessonsFor(craft)` → `{ id, skills, terms, notes, createSkills, createWords, createHint }` (the sail set, `src/lessons/sail.js`, names today's `sail/skills.js`, `ui/words.js`, `ui/skipper.js` NOTES and `ui/controlsHint.js`), and the sail controller builds its skill model, words, hint line and notes from it; a craft with no set is refused by name. tests/craftAudio, tests/lessons.
- Cruise's start in three parts (Phase C step 11): `src/modes/chill/index.js` `start` (54 lines, was 552) composes `voyage.js` `createVoyage(core, cx)` (the chart, the boat, the navigator and skipper, the director and camera rig, the fireworks trip, `sailFor`, the `chill` service; `settleCapture` for captures), `passenger.js` `createPassenger(core, v, cx)` (the music, the quiet line, the bar, dock and Locker, the look, keys and pad, the mark, the tools; `look`, `evening`, `frame` for the frame) and `handover.js` `createHandover(core, v, cx, P, { coreOptions })` (`takeHelm`, `handBack`, `update` while Sail's controls run). The state they share is one object, `cx` (`simT`, `tools`, `handed`, `leaving`, `music`, `line`, `controls`, `logbook`, `chartApi`, `blend`, `passenger`, `begun`, `takeHelm`, and the time / weather / wind / photo calls). Same creation order, same frame order.

A mode never imports another mode's folder, and the shared UI (`src/ui/`, `src/race/`) imports no mode code.

## The interface

```js
// required
export async function start(core) { …; return { update(dt) {}, dispose() {} }; }
// optional: what the core builds differently for this mode, read before the world is built
export function coreOptions(flags) { return { defaultHour: '18', wind: (hour) => ({ … }), createWake, hud: 'calm', card: 'sail', stage: true, firstSail: 'goal' }; }
```

- `start(core)` runs once the world is built, the reflection probe is captured and two warm-up frames are drawn (the sky's LUTs are ready). Load the mode's own assets here (the boat's GLBs). The `ready` service (`window.__lakeshore.ready` for the tools) resolves after `start` resolves, so a capture sees what `start` set up.
- `update(dt)` runs once per frame on live pages, before the core renders the frame. `dt` is the raw wall-clock step in seconds; clamp it yourself. Captures (`?headless`) have no loop: they call `renderOnce()` themselves, so a mode settles its capture state inside `start`.
- `dispose()` removes the mode's listeners and objects and keeps the core. A mode switch in play calls it (`core.switchMode`, below).

## Switching modes in play

`core.switchMode(import('./modes/<m>/index.js'), { params })` (params: a URLSearchParams, a query string or a flags object) disposes the running mode and starts the next on the same core: nothing reloads. The next mode's `coreOptions(flags)` gives only its time rate (or schedule) from then on; the world, the wind and the wake stay as built. `start(core)` gets a core whose `T0` is the scene time now, whose `flags` are the ones passed (frozen; src/core/flags.js) (the shell passes `?start=x,z&heading=deg` of the boat, so it stays where it is), and with `switched: true` (a gesture has already happened: Chill starts its music at once). The shell (`src/shell.js`) runs it behind the loading card's horizon line and writes `?mode=` with `history.replaceState`. A mode must dispose everything it made: its DOM, its listeners (an AbortController), its scene objects. What it provided to `core.services` goes with it: the core disposes the mode's scope after `dispose()` (a part that leaves earlier, as Cruise's hand-back, removes its own: `services.remove(name, obj)`).
- `coreOptions(flags)` (optional): `defaultHour` (the `?hour` default, a string), `wind(hour)` (options for the core's `WindField` instead of the steady base wind; return `null` for the base wind), `createWake` (a factory; the water reads the wake, so the core builds it just before the water), `timeRate` (game seconds per scene second without `?timerate`; Day Sail 10, default 0: the light stays). And what the shared UI does in this mode, in place of checks on the mode's name: `hud` (the Calm HUD's default, `'calm'` or `'full'`; Regatta full), `card` (the loading card's and the dock's look, `'sail'` or `'cruise'`), `stage` (the staged first visit plays here: Sail), `firstSail` (`'goal'` the first sail's lines and the island goal: Sail; `'offer'` a New player is offered the helm: Cruise), `fullscreenKey` (`false`: Shift+F is not full screen; Cruise). The core provides the options in force as the `modeOptions` service at boot and on a switch; Cruise's hand-over passes Sail's to the shell's `setMode('sail', options)`. A mode with no `coreOptions` (Fly) gets the defaults: calm, the Sail card, no stage, no first-sail lines, Shift+F full screen. **The schema** (`src/modes/options.js` MODE_OPTIONS): `hud`, `card`, `stage`, `firstSail`, `fullscreenKey`, `defaultHour`, `timeRate`, `timeSchedule`, `wind`, `createWake`, `ownFireworks` (a mode with its own show: the core's stays out). The core checks a mode's options at boot and on a switch (`checkModeOptions`): an unknown key or a bad value throws in dev (the Vite dev server, node), and in a build is dropped with one `console.error` (its reader's default applies). `tests/modeOptions.test.mjs` validates every mode's options.

## What `core` gives a mode

| Field | What |
|---|---|
| `flags`, `headless`, `msg`, `stage(name, f)` | the URL's flags (src/core/flags.js; frozen: a mode that changes one makes its own copy with `withFlags`), `?headless`, the `#msg` line, the loading card's stage hook |
| `T0`, `SEED`, `HOUR` | `?t`, `?seed`, the resolved hour |
| `renderer`, `scene`, `camera`, `atmosphere`, `sunWorld`, `elev` | the renderer and the sky (the sun's world direction and its height `sunWorld.y`) |
| `terrain`, `lod`, `wind`, `lum`, `wake`, `water`, `trees`, `landmarks`, `shoreline`, `harbour`, `traffic`, `audio`, `clouds`, `birds`, `storm` | the world (`src/core/world.js`); `lum` is the scene's luminance scale, `0.6 / exposure`; `storm` the thunderstorm (`src/weather/storm.js`: `start`, `choose`, `running`, `info`), which runs from the mode's start |
| `systems`, `env` | the world's per-frame systems and the frame's shared values (`src/core/systems.js`: `{ rain, shelter, hour, sun }`); the core runs them in its frame (`src/core/loop.js`), a mode only reads `env` |
| `tier` | the quality tier the world was built with (`src/quality/apply.js` tierFor: the tiers.js table plus a phone's cuts): pass its knobs to what a mode builds (the air's pools `tier.air`, the boat's textures `tier.ktx2.boat`) |
| `renderOnce()` | draws one frame (the capture contract's) |
| `afterFrame(fn)` | `fn(canvas)` runs once, right after the next frame is drawn, in the same task (the only time a WebGPU canvas can be read: `drawImage` after `renderOnce()` resolves is black). Keep it short |
| `time`, `setTime(t)` | the scene clock (wind, water, clouds, and the time of day); a mode that owns time sets it every frame |
| `clock`, `daylight`, `sun` | D2, the time of day: the `TimeOfDay` clock (`clock.hourOfDay(t)`, `setRate`, `setHour`), the daylight that applies it, and `sun = { hour, elevationDeg, direction, exposure, light }`, updated every frame before the render. `sunWorld` stays live; `elev` is the start hour's |

## Rules

- No mode code in the core. Anything only one mode needs lives in that mode's folder and is imported from there.
- A mode's assets load through the mode, not at the top level of a core module.
- Keep it deterministic by URL: a capture of a mode must not depend on wall-clock time.
- A mode shares objects through `core.services` (src/core/services.js): `provide(name, obj)`, `get(name)`, `has(name)`, `remove(name, obj?)` (Day Sail: `boat` = `{ phys, boat, follow, env }`, the sloop's parts, read only by the sail code; `player` = `{ craft, kind, view(), phys, follow, group, addPost, cue }` (`src/core/player.js`), what everything else reads: the shell, the HUD, the watchdog, the birds, the fireworks, the kayaks; `modeOptions` (the core's: the mode in force's coreOptions), `hint`, `controls`). Pass `core` or the registry to what needs it; read a reference that lives as long as the reader once, not per frame. Never read `window.__lakeshore` in game code: it is a read-only mirror of the registry for the tools, probes and films (src/core/mirror.js; tests/services.test.mjs checks).
